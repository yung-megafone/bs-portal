Policy

Security posture.

B.S. Portal has meaningful security controls, but the current release is still alpha software.

Current master / active alpha · Best-effort security support

Do not publish vulnerabilities, credentials, private records, or exploitable proofs-of-concept in a public issue. Use GitHub private vulnerability reporting/security advisories when available, or a private contact method published by the repository owner.

Current security boundary

  • Django authentication, session, CSRF, and clickjacking protections provide the framework baseline.
  • Operational pages require authentication where appropriate.
  • State-changing workflows enforce authorization on the server rather than trusting client controls.
  • SHIT separates ticket visibility from ticket-management authority.
  • Board status and queue-order mutations are server-authorized and validated.
  • BAM requesters can submit their own resource needs, while reservation operations are restricted to staff/superusers or manager/admin members of the relevant owning department.
  • Reservation conflicts are checked server-side inside transactions; browser availability displays are not authoritative.
  • BAM reservations do not silently rewrite physical custody.
  • Domain histories improve accountability but are not yet a tamper-proof centralized audit ledger.

Alpha deployment restrictions

  • Use synthetic/disposable data in publicly reachable staging environments.
  • Never expose Django with DEBUG=True to the public internet.
  • Keep secrets and machine-specific credentials outside source control.
  • Review migrations and verify backups before applying schema changes to valuable data.
  • Do not treat Django admin as a routine least-privilege operator interface.
  • Do not assume the current application authorization model is the final production RBAC design.

Production baseline

Before BSP is treated as production-ready, deployments should verify:

  • DEBUG=False, explicit hosts/origins, and HTTPS/TLS at the public boundary.
  • Secure session/CSRF cookie configuration and reviewed security headers.
  • Least-privilege database, filesystem, and administrative access.
  • Private protection of environment files, uploaded media, logs, and backups.
  • Tested backup and restore procedures.
  • Dependency/security updates and authorization tests for privileged workflows.
  • An incident-response and credential-rotation procedure.

Uploads and operational data

BAM evidence and SHIT attachments are untrusted user-controlled content. Deployments should keep media outside executable/static paths, prevent execution of uploads, enforce sensible size limits, avoid trusting filename/MIME claims, and consider content scanning before broad production exposure.

Planned hardening

Major remaining work includes a formal authorization matrix, MFA/passkeys, rate limiting, stronger database role separation, centralized/database-enforced append-only auditing, production cookie/header review, CSP evaluation, dependency/static analysis, upload scanning strategy, backup/restore drills, threat modeling, and deployment review.

Privacy-sensitive security

Security controls should protect operational records without turning BSP into an employee-surveillance platform. The reference Timeclock design intentionally avoids GPS tracking, biometrics, device fingerprints, advertising IDs, and continuous-presence telemetry. See the Privacy Policy.
